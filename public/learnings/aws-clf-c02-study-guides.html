Exam mechanics (from the guide's front matter)

  • 50 scored questions + 15 unscored (unidentified, don't affect score) = 65 total questions seen, 90 minutes.
  • Question types: multiple choice (1 correct + 3 distractors) and multiple response (2+ correct out of 5+ options).
  • Scoring: scaled 100–1,000, passing score 700. No penalty for guessing — never leave a question blank.
  • Compensatory scoring model — you don't need to pass each domain individually, only the overall exam. Don't panic over one weak domain if the others are strong, but domain weighting still tells you where to spend study time (see below).
  • Target candidate: up to 6 months of AWS exposure, "independent of a specific job role" — explicitly not expected to know coding, cloud architecture design, troubleshooting, implementation, or load/ performance testing. If a practice question asks you to design or debug something in depth, that's a sign it's testing beyond CLF-C02's actual scope (or it's really an Associate-level question mislabeled).

Domain 1: Cloud Concepts (24%)

Task Statement 1.1 — Define the benefits of the AWS Cloud

Knowledge of: value proposition of the AWS Cloud.

Skills in:

  • Understanding economies of scale (cost savings)
  • Understanding benefits of global infrastructure (speed of deployment, global reach)
  • Understanding advantages of high availability, elasticity, and agility

Study note: this is the "six advantages of cloud computing" material — covered in full in Essentials tab, §1. Be able to name the advantage a scenario is describing, not just recite the list.

Task Statement 1.2 — Identify design principles of the AWS Cloud

Knowledge of: AWS Well-Architected Framework.

Skills in:

  • Understanding the pillars (operational excellence, security, reliability, performance efficiency, cost optimization, sustainability)
  • Identifying differences between the pillars — this phrasing is a direct signal the exam gives you a scenario and asks which single pillar it best fits, so precision matters, not just the list.

Study note: full pillar-by-pillar definitions in Essentials tab, §8. Drill: given a scenario ("a team wants to reduce energy consumption," "a team wants systems to recover automatically from failure"), name the one pillar, not two.

Task Statement 1.3 — Understand the benefits of and strategies for migration to the AWS Cloud

Knowledge of:

  • Cloud adoption strategies
  • Resources to support the cloud migration journey

Skills in:

  • Understanding the benefits of the AWS Cloud Adoption Framework (AWS CAF) — reduced business risk; improved ESG (environmental, social, governance) performance; increased revenue; increased operational efficiency
  • Identifying appropriate migration strategies (e.g., database replication, use of AWS Snowball)

Study note: CAF's six perspectives and the "7 R's" of migration (updated from the original 6 — AWS added Relocate as its own strategy) are in Essentials tab, §9. New here vs. that doc: the exam explicitly frames CAF's benefits around ESG language — memorize that specific acronym, it's the kind of precise term the exam likes to test as a distractor-bait phrase. Migration tools themselves (DMS, SCT, Snow Family, Application Discovery Service, MGN, Migration Hub, Transfer Family) are detailed in Services tab under Migration and Transfer.

Task Statement 1.4 — Understand concepts of cloud economics

Knowledge of:

  • Aspects of cloud economics
  • Cost savings of moving to the cloud

Skills in:

  • Understanding fixed costs vs. variable costs
  • Understanding costs associated with on-premises environments
  • Understanding licensing strategy differences: Bring Your Own License (BYOL) vs. included licenses
  • Understanding the concept of rightsizing
  • Identifying benefits of automation (e.g., provisioning/configuration management with AWS CloudFormation)
  • Identifying managed AWS services (e.g., RDS, ECS, EKS, DynamoDB)

Study note: this task statement introduces terms not yet covered elsewhere in this note set — add these to your vocabulary explicitly:

  • Rightsizing — matching instance/resource types and sizes to actual workload needs, to avoid paying for unused capacity. (Compare to AWS Compute Optimizer's job, in Services tab.)
  • BYOL vs. included license — BYOL means you bring an existing software license (e.g., an on-prem Windows Server or Oracle license) and only pay AWS for the infrastructure; "included license" pricing bundles the software license cost into the AWS hourly rate. Relevant to EC2/RDS pricing decisions and to AWS License Manager.
  • Managed service as a concept — AWS operates the underlying infrastructure (patching, scaling, backups) so the customer focuses on configuration and data, not servers. This is the general concept behind why RDS is "less operational burden" than self-hosting a database on EC2 — a recurring exam framing ("which is a managed service" / "why would a company choose RDS over EC2 with a database installed").
Domain 2: Security and Compliance (30% — the single biggest domain)

Task Statement 2.1 — Understand the AWS shared responsibility model

Knowledge of: AWS shared responsibility model.

Skills in:

  • Recognizing its components
  • Describing the customer's responsibilities on AWS
  • Describing AWS's responsibilities
  • Describing shared responsibilities
  • Describing how responsibilities shift depending on the service used (e.g., RDS, Lambda, EC2)

Study note: full model in Essentials tab, §6, plus the official diagram breakdown transcribed below (§ "Shared Responsibility Model — official diagram breakdown"). The "shifts depending on the service" skill is the highest-yield drill: for EC2 you patch the guest OS; for RDS AWS patches the OS; for Lambda AWS manages everything except your code and data. Practice naming the split for all three explicitly, not just EC2.

Task Statement 2.2 — Understand AWS Cloud security, governance, and compliance concepts

Knowledge of:

  • AWS compliance and governance concepts
  • Benefits of cloud security (e.g., encryption)
  • Where to capture and locate logs associated with cloud security

Skills in:

  • Identifying where to find AWS compliance information (e.g., AWS Artifact)
  • Understanding compliance needs among geographic locations/industries (AWS Compliance programs)
  • Describing how customers secure resources on AWS (Amazon Inspector, AWS Security Hub, Amazon GuardDuty, AWS Shield)
  • Identifying different encryption options (encryption in transit, encryption at rest)
  • Recognizing services that aid governance/compliance: monitoring with CloudWatch; auditing with CloudTrail, AWS Audit Manager, and Config; reporting with access reports
  • Recognizing compliance requirements vary among AWS services

Study note: memorize the specific verb attached to each service — the exam tests this pairing directly:

  • Monitoring → CloudWatch
  • Auditing → CloudTrail, Audit Manager, Config
  • Reporting → access reports (e.g., IAM access reports/Access Analyzer findings)
  • Compliance documents on demand → AWS Artifact

Encryption in transit (data moving over a network, e.g., TLS/HTTPS) vs. encryption at rest (data stored on disk, e.g., S3/EBS/RDS encryption via KMS) is a clean, frequently-tested distinction — know which AWS feature handles which for at least S3, EBS, and RDS.

Task Statement 2.3 — Identify AWS access management capabilities

Knowledge of:

  • Identity and access management (IAM)
  • Importance of protecting the AWS root user account
  • Principle of least privilege
  • AWS IAM Identity Center (AWS Single Sign-On)

Skills in:

  • Understanding access keys, password policies, credential storage (AWS Secrets Manager, AWS Systems Manager)
  • Identifying authentication methods (MFA, IAM Identity Center, cross-account IAM roles)
  • Defining groups, users, custom policies, and managed policies under least privilege
  • Identifying tasks that only the root user can perform
  • Understanding root user protection methods
  • Understanding identity management types (e.g., federated)

Study note: "tasks that only the root user can perform" is a concrete, memorizable list the exam likes — examples include: changing the account's support plan, closing the AWS account, changing/viewing the account's payment currency, restoring IAM user permissions if accidentally revoked, registering as a seller in the Reserved Instance Marketplace, and some account-level settings changes. You don't need the exhaustive list, but internalize the pattern: root user tasks are account-level, billing-level, or "break glass" actions — not day-to-day resource management, which should always be an IAM user/role. Federated identity = authenticating via an external identity provider (corporate Active Directory, Google, etc.) rather than a native IAM user — this is what IAM Identity Center and Cognito both enable in different contexts (workforce vs. customer-facing, respectively).

Task Statement 3.2 — Define the AWS global infrastructure

Knowledge of:

  • Regions, Availability Zones, edge locations

  • Benefits of edge locations
  • AWS Wavelength Zones and AWS Local Zones

Skills in:

  • Describing relationships among Regions/AZs/edge locations
  • Describing how to achieve HA using multiple AZs
  • Recognizing that AZs do not share single points of failure
  • Describing when to use multiple Regions (disaster recovery, business continuity, low latency for end users, data sovereignty)

Task Statement 3.3 — Identify AWS compute services

Skills in:

  • Recognizing appropriate use of different EC2 instance types (e.g., compute optimized, storage optimized)
  • Recognizing appropriate use of different container options (ECS, EKS)
  • Recognizing appropriate use of different serverless compute options (Fargate, Lambda)
  • Recognizing that auto scaling provides elasticity
  • Identifying the purposes of load balancers

Study note: EC2 instance type families are worth knowing at a high level even though this doc's service tables don't break them out:

  • General purpose (e.g., M-family) — balanced CPU/memory, default choice for most workloads
  • Compute optimized (C-family) — high-performance processors, for CPU-bound workloads (batch processing, gaming servers, scientific modeling)
  • Memory optimized (R/X-family) — for workloads processing large datasets in memory (in-memory databases, real-time big data analytics)
  • Storage optimized (I/D-family) — high, fast local disk I/O (NoSQL databases, data warehousing, distributed file systems)
  • Accelerated computing (P/G-family) — GPU/hardware accelerators (ML training, graphics rendering)

You just need to match a workload description to the right category name, not memorize instance size codes.

Task Statement 3.4 — Identify AWS database services

Skills in:

  • Deciding when to use EC2-hosted databases vs. AWS managed databases
  • Identifying relational databases (RDS, Aurora)
  • Identifying NoSQL databases (DynamoDB)
  • Identifying memory-based databases
  • Identifying database migration tools (AWS DMS, AWS SCT)

Study note: "memory-based databases" = ElastiCache and MemoryDB for Redis, both covered in Services tab under Database. The EC2-hosted-vs-managed decision is the Domain 1.4 "managed services" concept applied specifically to databases: self-managing a database on EC2 gives full control (needed for an unsupported engine/version or deep custom tuning) at the cost of operational burden; RDS/Aurora/ DynamoDB trade that control for AWS handling patching, backups, and failover.

Task Statement 3.6 — Identify AWS storage services

Skills in:

  • Identifying uses for object storage
  • Recognizing differences in S3 storage classes
  • Identifying block storage solutions (EBS, instance store)
  • Identifying file services (EFS, FSx)
  • Identifying cached file systems (AWS Storage Gateway)
  • Understanding use cases for lifecycle policies
  • Understanding use cases for AWS Backup

Study note: two terms not yet called out elsewhere in this note set:

  • Instance store — temporary block-level storage physically attached to the host machine an EC2 instance runs on. Data is lost if the instance stops, terminates, or the underlying hardware fails — unlike EBS, which persists independently of the instance. Use case: purely temporary data (cache, buffer, scratch space) where loss is acceptable, in exchange for very high, low-latency local I/O.
  • S3 lifecycle policies — rules that automatically transition objects between storage classes (e.g., Standard → Standard-IA → Glacier) or expire/delete them after a set number of days, without manual intervention. This is how you actually apply the storage class differences from Essentials tab, §5 over time, e.g., "move to Glacier after 90 days, delete after 7 years."

Storage Gateway is specifically labeled a "cached file system" here — its file gateway mode caches frequently accessed data locally on-prem while storing the full dataset in S3, which is the nuance the exam wants beyond just "hybrid storage."

Domain 4: Billing, Pricing, and Support (12%)

Task Statement 4.1 — Compare AWS pricing models

Knowledge of:

  • Compute purchasing options (On-Demand, Reserved Instances, Spot Instances, Savings Plans, Dedicated Hosts, Dedicated Instances, Capacity Reservations)
  • Data transfer charges
  • Storage options and tiers

Skills in:

  • Identifying/comparing when to use various compute purchasing options
  • Describing Reserved Instance flexibility
  • Describing Reserved Instance behavior in AWS Organizations
  • Understanding incoming vs. outgoing data transfer costs (e.g., Region-to-Region vs. within the same Region)
  • Understanding pricing options across storage options/tiers

Study note: EC2 pricing models themselves are in Essentials tab, §3, but two specifics the exam guide calls out that aren't detailed there yet:

  • Reserved Instance flexibility — RIs can be flexible in instance size within the same instance family (e.g., you can apply an m5 family RI's discount across different m5 sizes) and can be modified (AZ, network platform, instance size within family) during their term; Convertible RIs additionally allow changing the instance family itself, at a smaller discount than Standard RIs.
  • RI behavior in AWS Organizations — by default, RI discounts and Savings Plans automatically apply across all linked accounts in an Organization with consolidated billing, not just the account that purchased them — this "shared" behavior can be turned off per-account if needed.
  • Data transfer costs, general rule: data transfer IN to AWS is free in virtually all cases; data transfer OUT to the internet is charged (tiered, decreasing per-GB as volume grows); transfer between Regions is charged; transfer within the same Region between AZs typically has a small charge, while transfer within the same AZ (or via a VPC endpoint/same Region as applicable) can be free — the exam wants the general shape (in-free, out-charged, cross-Region-charged) more than exact rates.
  • Capacity Reservations vs. Reserved Instances — a Capacity Reservation reserves EC2 capacity in a specific AZ with no commitment to a term or discount; it guarantees availability, not savings. RIs are the reverse: a billing/discount construct, not a capacity guarantee (though Regional RIs don't guarantee capacity at all). Don't conflate the two.

Task Statement 4.2 — Understand resources for billing, budget, and cost management

Knowledge of:

  • Billing support and information
  • Pricing information for AWS services
  • AWS Organizations
  • AWS cost allocation tags

Skills in:

  • Understanding appropriate uses/capabilities of AWS Budgets, AWS Cost Explorer, and AWS Billing Conductor
  • Understanding appropriate uses/capabilities of AWS Pricing Calculator
  • Understanding AWS Organizations consolidated billing and allocation of costs
  • Understanding types of cost allocation tags and their relation to billing reports (e.g., AWS Cost and Usage Report)

Study note: cost allocation tags are the one genuinely new concept here — key-value labels (e.g., Project: bfg-platform, Environment: prod) attached to AWS resources, which can then be activated in Billing so cost reports (like the Cost and Usage Report) can be broken down and filtered by tag. This is the mechanism behind "which team/project is spending what" — the practical link between tagging discipline and being able to answer that question later. Two tag types: AWS-generated (e.g., aws:createdBy, automatic) and user-defined (whatever your org decides). All four billing tools (Budgets, Cost Explorer, Billing Conductor, Pricing Calculator) are in Services tab under Cloud Financial Management.

Amazon EC2

Compute

Resizable virtual machines ("instances") in the cloud

Used forRunning any general-purpose workload where you need control over the OS — web servers, batch jobs, custom software
Examples & exam cues
  • A company hosts its Node.js web app on EC2 instances behind a load balancer; a data team spins up a large-memory EC2 instance overnight to run a heavy Spark job, then shuts it down

AWS Lambda

Compute

Serverless, event-driven functions — code runs only in response to a trigger, no server management

Used forShort-lived, event-triggered processing: image resizing on upload, API backends, scheduled cleanup jobs
Examples & exam cues
  • An S3 upload triggers a Lambda function that generates a thumbnail; a nightly EventBridge schedule triggers a Lambda that archives old DynamoDB records

AWS Elastic Beanstalk

Compute

Deploy and manage applications without needing to know the underlying infrastructure

Used forFast deployment for common app stacks (Java, .NET, Node.js, Python, etc.) without manually configuring infrastructure
Examples & exam cues
  • A small team deploys a Django app by uploading a zip file; Beanstalk provisions the EC2 instances, ELB, and Auto Scaling group automatically

AWS Batch

Compute

Fully managed batch computing service

Used forRunning large numbers of batch jobs (scientific computing, rendering, ETL) without managing job schedulers/clusters
Examples & exam cues
  • A genomics lab runs thousands of parallel DNA-sequencing jobs; a media company batch-transcodes video files overnight

Amazon Lightsail

Compute

Launch projects quickly from a simple management interface, with bundled, predictable pricing

Used forSimple websites, dev/test environments, small applications without needing full AWS complexity
Examples & exam cues
  • A freelancer hosts a WordPress blog on Lightsail; a student spins up a low-cost sandbox VM for a class project

AWS Outposts

Compute

Extends AWS infrastructure, services, APIs, and tools to customer premises

Used forRunning AWS-managed compute on-site for latency or data-residency reasons
Examples & exam cues
  • A hospital runs patient-imaging workloads on an Outposts rack in its own data center because data must stay on-premises, while still using the same AWS APIs as the rest of its fleet

AWS Local Zones

Compute

Extends a Region to place AWS compute and storage closer to large population and industry centers

Used forReducing latency for applications that need to be near end users, without a full separate Region
Examples & exam cues

1. Cloud Computing Fundamentals

What "cloud computing" means on the exam: on-demand delivery of IT resources over the internet with pay-as-you-go pricing — no owning or maintaining physical data centers.

Deployment models

ModelDescriptionExample use case
CloudAll infrastructure runs in the cloudA startup with no legacy systems runs 100% on AWS
On-premises (private cloud)Resources run in your own data center, but managed with cloud-like tooling (virtualization, self-service)A bank keeps sensitive workloads on-prem for regulatory reasons
HybridA mix of on-premises and cloud, connected (e.g., via Direct Connect/VPN)A company keeps its legacy mainframe on-prem but bursts extra compute to AWS during peak load

Six advantages of cloud computing (memorize all six — recurring exam theme)

  1. Trade capital expense for variable expense — pay for what you use instead of investing upfront in data centers/hardware.
  2. Benefit from massive economies of scale — AWS aggregates usage from hundreds of thousands of customers, driving lower pay-as-you-go prices.
  3. Stop guessing capacity — scale based on actual demand instead of forecasting and over/under-provisioning.
  4. Increase speed and agility — new resources are available in minutes, lowering the cost of experimentation.
  5. Stop spending money running and maintaining data centers — focus on projects that differentiate the business, not racking servers.
  6. Go global in minutes — deploy applications in multiple Regions worldwide with a few clicks.

Core terms the exam expects you to distinguish

  • High availability — a system designed to remain operational and accessible with minimal downtime, typically by removing single points of failure (e.g., spanning multiple AZs).
  • Elasticity — the ability to automatically scale resources up or down to match actual demand (see Compute Concepts below).
  • Agility — the ability to provision new resources in minutes rather than weeks, lowering the cost of experimentation.
  • Scalability — the ability of a system to handle growth in load, whether by scaling up (vertical) or out (horizontal).
  • Fault tolerance — the ability of a system to keep working correctly even when one or more of its components fail.
  • Durability — the likelihood that stored data survives over time without being lost or corrupted (e.g., S3's 11 nines, below).

These five terms are easy to conflate — a scenario naming one specific outcome ("stays up during an AZ failure" = fault tolerance/high availability; "handles Black Friday traffic automatically" = elasticity) is testing precise recall, not a vague sense that "cloud is flexible."

Service models (not AWS-specific, but tested)

  • IaaS (Infrastructure as a Service) — rent networking, computers, data storage space. Example: EC2, EBS.
  • PaaS (Platform as a Service) — removes the need to manage underlying infrastructure, focus on deployment/management of applications. Example: Elastic Beanstalk, RDS.
  • SaaS (Software as a Service) — complete product run and managed by the service provider. Example: Gmail, or a business app built entirely on AWS and consumed by end users.

2. AWS Global Infrastructure

  • Region — a physical geographic location with multiple, isolated Availability Zones (e.g., us-east-1 = N. Virginia). Choose a Region based on: compliance (data residency laws, also called data sovereignty — same concept, both phrasings appear on the exam), proximity (latency to users), feature availability (not all services launch in every Region simultaneously), and pricing (costs vary by Region). Also drives the choice to use multiple Regions: disaster recovery, business continuity, low latency for distant end users, or data sovereignty requirements.
  • Availability Zone (AZ) — one or more discrete data centers with redundant power/networking, isolated from failures in other AZs, but connected via high-bandwidth, low-latency links. Every Region has a minimum of 3 AZs.
  • Edge Location — site used by CloudFront to cache content closer to end users, reducing latency; far more numerous than Regions/AZs.
  • AWS Local Zones — extend a Region to place compute/storage closer to large population centers for latency-sensitive apps, over standard networks.
  • AWS Wavelength — embeds AWS compute/storage within telecom providers' 5G networks specifically for ultra-low-latency mobile device use cases. Don't confuse with Local Zones: Local Zones = closer to population/industry centers generally; Wavelength = inside a 5G carrier network specifically, for mobile latency.
  • AWS Outposts — physical rack of AWS-managed infrastructure installed in a customer's own data center, for workloads needing to stay on-prem but managed the AWS way.

Key exam trap: an AZ is not the same as a data center — an AZ can contain multiple data centers, and Regions are made of multiple AZs, not the reverse.

Ways to interact with AWS

  • AWS Management Console — browser-based GUI.
  • AWS CLI — command-line, scriptable.
  • AWS SDKs — language-specific libraries (Python/boto3, JS, Java, etc.) to call AWS APIs from application code.

3. Compute Concepts

EC2 instance type families

FamilyOptimized forExample use case

Memory optimized (R/X-family)Large in-memory datasetsIn-memory databases, real-time big data analytics
Storage optimized (I/D-family)High, fast local disk I/ONoSQL databases, data warehousing, distributed file systems

  • Vertical scaling — increasing the size (CPU/RAM) of an existing instance. Has a ceiling (max instance size) and usually requires a restart.
  • Horizontal scaling — adding more instances of the same size. This is what "elasticity" in AWS typically refers to, and it's what Auto Scaling Groups do.
  • Auto Scaling — automatically adds/removes EC2 instances based on demand (e.g., CloudWatch alarms on CPU utilization), maintaining application availability while controlling cost.
  • EC2 pricing models:
    • On-Demand — pay by the second/hour, no commitment, highest per-unit price. Best for short-term, unpredictable workloads.
    • Reserved Instances (RI) — 1 or 3-year commitment for a discount (up to ~75%) vs. On-Demand. Best for steady-state, predictable usage.
    • Savings Plans — similar discount model to RIs but flexible across instance family/Region, committing to a consistent $/hour spend.
    • Spot Instances — bid on spare EC2 capacity for up to ~90% discount; AWS can reclaim with a 2-minute interruption notice. Best for fault-tolerant, flexible workloads (batch jobs, CI/CD runners).
    • Dedicated Hosts — physical server dedicated entirely to you, for licensing (bring-your-own-license) or compliance requirements.
    • Dedicated Instances — EC2 instances in a VPC dedicated to you (no shared-tenancy hardware), but unlike Dedicated Hosts, no long-term commitment required — pay by the second, like On-Demand.
    • On-Demand Capacity Reservations — reserves EC2 capacity in a specific AZ with no term commitment and no billing discount — it guarantees availability, not savings. Don't confuse with RIs, which are the reverse: a billing/discount construct that doesn't necessarily guarantee capacity.
  • Reserved Instance flexibility — a Standard RI can be modified (AZ, network platform, instance size within the same family) during its term; a Convertible RI additionally allows changing the instance family itself, at a smaller discount than a Standard RI.
  • RI / Savings Plans behavior in AWS Organizations — by default, these discounts automatically apply across all linked accounts under consolidated billing, not just the account that purchased them (this sharing can be turned off per-account if needed).
  • Serverless — no server provisioning/management at all; you deploy code (Lambda) or containers (Fargate) and AWS runs them on demand.
  • Rightsizing — matching instance/resource types and sizes to actual workload needs, to avoid paying for unused capacity (what AWS Compute Optimizer automates).
  • BYOL vs. included license — Bring Your Own License (BYOL) means using an existing owned software license (e.g., on-prem Windows Server or Oracle) and paying AWS only for infrastructure; "included license" pricing bundles the software license cost into the AWS hourly rate.
  • Managed service (concept) — AWS operates the underlying infrastructure (patching, scaling, backups) so the customer focuses on configuration and data, not servers — e.g., RDS/ECS/EKS/DynamoDB are managed services; the same workload self-hosted on EC2 is not.

4. Networking Concepts

  • Amazon VPC — your own logically isolated section of the AWS cloud, with full control over IP address ranges, subnets, route tables, and gateways.
  • Subnet — a range of IP addresses within a VPC; public subnet routes to an Internet Gateway, private subnet does not.
  • Internet Gateway — allows communication between a VPC and the internet; attached at the VPC level.
  • NAT Gateway — allows instances in a private subnet to initiate outbound internet traffic (e.g., for software updates) without being directly reachable from the internet.
  • Network ACL (NACL) — an optional, virtual firewall that controls inbound and outbound traffic at the subnet level, acting as an additional layer of defense on top of security groups. Every subnet in a VPC is automatically associated with a NACL (the VPC's default NACL allows all inbound and outbound traffic by default; a custom NACL denies all traffic by default until rules are added). Because a NACL sits at the subnet boundary, it applies to every instance in that subnet, regardless of which security group those instances individually use — making it the right tool for a blanket rule (e.g., "block this one malicious IP from an entire subnet") that would otherwise mean updating every instance's security group individually.
  • Security Group vs. Network ACL (recurring exam favorite):
Security GroupNetwork ACL

  • Elastic Load Balancing (ELB) — distributes incoming traffic across multiple targets. Types: Application Load Balancer (Layer 7, HTTP/ HTTPS, path/host-based routing), Network Load Balancer (Layer 4, TCP/UDP, extreme performance/static IP), Gateway Load Balancer (deploying/scaling third-party virtual network appliances).
  • Amazon Route 53 — DNS service; routing policies include simple, weighted, latency-based, geolocation, and failover routing.
  • Amazon CloudFront — CDN; caches content at edge locations.
  • Direct Connect vs. VPN: Direct Connect = dedicated private physical connection (consistent bandwidth, no public internet); VPN = encrypted tunnel over the public internet (faster to set up, variable performance).

5. Storage & Database Concepts

S3 fundamentals

  • Object storage — objects (files) live in buckets, addressed by key.
  • Durability: 99.999999999% ("11 nines") for standard storage classes — this is a specific, frequently-tested number.
  • Storage classes (highest to lowest cost, most to least frequently accessed): S3 Standard → S3 Intelligent-Tiering → S3 Standard-IA (infrequent access) → S3 One Zone-IA → S3 Glacier Instant Retrieval → S3 Glacier Flexible Retrieval (minutes–hours) → S3 Glacier Deep Archive (cheapest, up to 12 hours retrieval).
  • S3 is NOT a file system — no POSIX compliance, no direct "mount" to an OS the way EFS is (S3 access is via API/HTTP).
  • S3 lifecycle policies — rules that automatically transition objects between storage classes over time (e.g., Standard → Standard-IA → Glacier) or expire/delete them after a set number of days, without manual intervention — this is how the storage-class differences above actually get applied over an object's life (e.g., "move to Glacier after 90 days, delete after 7 years").

  • AWS Storage Gateway — hybrid storage connecting an on-premises software appliance to cloud storage; its file gateway mode is specifically a "cached file system" — it caches frequently accessed data locally on-prem while storing the full dataset in S3, giving local-speed access without keeping everything on-site.
  • AWS Backup — a single, policy-driven backup plan that centralizes and automates backups across multiple AWS storage/database services (and on-premises), instead of separate ad-hoc backup scripts per service.

Databases

  • Relational (SQL) — structured schema, tables with relationships. AWS: RDS, Aurora. Best for transactional systems needing ACID guarantees (banking, order systems).
  • Non-relational (NoSQL) — flexible/no fixed schema. AWS: DynamoDB (key-value/document). Best for massive scale, simple access patterns, low and consistent latency.
  • Data warehouse — optimized for large-scale analytical queries over historical data, not transactional writes. AWS: Redshift.
  • In-memory / memory-based databases — reduce load on primary databases (or serve as the primary store itself) by keeping hot data in memory. AWS: ElastiCache (caching layer, Redis/Memcached) and MemoryDB for Redis (durable, can serve as the system of record, not just a cache).
  • EC2-hosted vs. AWS managed databases — self-managing a database on EC2 gives full control (needed for an unsupported engine/version or deep custom tuning) at the cost of operational burden (you patch, back up, and handle failover yourself); RDS/Aurora/DynamoDB trade that control for AWS handling patching, backups, and failover — the managed-service tradeoff from §3 applied specifically to databases.

6. Security, Identity & Compliance

The Shared Responsibility Model (heavily tested — know this cold)

  • AWS is responsible for security OF the cloud: physical facilities, hardware, network infrastructure, virtualization/hypervisor layer.
  • Customer is responsible for security IN the cloud: guest OS patching (for EC2), network/firewall configuration, IAM users/permissions, data encryption choices, application-level security.
  • The exact split shifts depending on the service's abstraction level: for managed services like RDS or DynamoDB, AWS takes on more (e.g., OS patching), leaving the customer responsible mainly for access control and data.

IAM core concepts

  • User — represents a person or application with long-term credentials.
  • Group — a collection of users sharing the same permissions.
  • Role — a set of permissions assumed temporarily (by a user, application, or AWS service) — no long-term credentials attached; the recommended way to grant EC2/Lambda access to other AWS services.
  • Cross-account IAM role — a role in one AWS account that a principal (user/role) from a different account can assume, granting temporary cross-account access without sharing long-term credentials.
  • Policy — a JSON document defining permissions (allow/deny actions on resources); can be managed (reusable, AWS- or customer-created) or custom/inline (attached directly to one identity).
  • Principle of least privilege — grant only the minimum permissions needed.
  • Multi-factor authentication (MFA) — a second authentication factor (e.g., a one-time code from a device/app) beyond a password, addable to any IAM user or the root user for stronger login security.
  • Federated identity — authenticating via an external identity provider (corporate Active Directory, Google, etc.) instead of a native, long-term IAM user. This is the mechanism behind:
    • AWS IAM Identity Center (formerly AWS Single Sign-On) — lets workforce users sign in once via a federated identity to access multiple AWS accounts and business apps, instead of separate IAM users per account.
    • Amazon Cognito — the same federated-identity concept, but aimed at customer-facing web/mobile app sign-in rather than workforce SSO.
  • Root user — the account owner; best practice is to enable MFA on it and avoid using it for daily tasks, creating IAM users/roles instead. A handful of actions are root-user-only and cannot be delegated to any IAM identity no matter its permissions — the pattern to remember is account-level, billing-level, or "break glass" actions, e.g., changing the account's Support plan, closing the AWS account, changing the account's payment currency, and restoring accidentally revoked IAM permissions. Day-to-day resource management should never need the root user.
  • IAM is global, not Region-specific — a user/role is usable across all Regions once created.

Key security services (see Services tab for full detail)

  • GuardDuty — threat detection.
  • Macie — sensitive data discovery in S3.
  • Inspector — vulnerability assessment.
  • Security Hub — aggregates findings from GuardDuty, Inspector, Macie, and partner tools into one dashboard.
  • Shield — DDoS protection.
  • WAF — web application firewall.
  • KMS — encryption key management.
  • Artifact — on-demand compliance reports.
  • Audit Manager — continuously collects evidence against a compliance framework (e.g., PCI DSS), instead of a manual annual scramble.
  • AWS Organizations + SCPs — multi-account governance guardrails.
  • AWS Marketplace — where third-party security products (firewalls, scanners, etc.) can be found and deployed on AWS.

Encryption

  • Encryption in transit — protects data as it moves across a network (e.g., TLS/HTTPS).
  • Encryption at rest — protects data while it is stored (e.g., S3, EBS, RDS encryption via KMS).
  • These are a clean, frequently-tested distinction — know which AWS feature/setting handles which for at least S3, EBS, and RDS.

Where to find AWS security information (pure recall — know they exist, not how to use them)

  • AWS Knowledge Center, AWS Security Center, AWS Security Blog — official sources for security guidance and announcements.
  • AWS re:Post and AWS Prescriptive Guidance — community Q&A and official best-practice implementation guidance, respectively (see §10 for the broader "AWS technical resources" list these belong to).

Compliance

  • AWS aligns with numerous global compliance programs (PCI DSS, HIPAA eligibility, GDPR, SOC 1/2/3, ISO 27001, FedRAMP). The exam expects you to know AWS provides the infrastructure and attestations, not that it automatically makes your specific workload compliant — compliance of the application is a shared responsibility.

8. AWS Well-Architected Framework — the six pillars (know each in one sentence)

  1. Operational Excellence — run and monitor systems to deliver business value; continually improve processes/procedures.
  2. Security — protect information, systems, and assets through risk assessments and mitigation.
  3. Reliability — ensure a workload performs its function correctly and consistently, recovering quickly from failure.
  4. Performance Efficiency — use computing resources efficiently and maintain efficiency as demand and technology evolve.
  5. Cost Optimization — avoid unneeded costs, run at the lowest price point that meets requirements.
  6. Sustainability — minimize environmental impacts of running cloud workloads.

Security pillar — the seven design principles

The Security pillar isn't just a one-line definition — the Well- Architected Framework backs it with seven specific design principles worth knowing by name, since the exam can present a scenario and ask which principle it demonstrates:

  1. Implement a strong identity foundation — enforce least privilege and separation of duties, with appropriate authorization for every interaction, centralizing identity management and reducing (or eliminating) reliance on long-term credentials.
  2. Enable traceability — monitor, alert, and audit actions and changes to the environment in real time by integrating logging and metrics with systems to automatically respond and take action.
  3. Apply security at all layers — apply a defense-in-depth approach with multiple security controls, rather than relying on a single layer (e.g., only an edge network firewall).
  4. Automate security best practices — use automated, software-based security mechanisms to improve the ability to securely scale more rapidly and cost-effectively than relying on manual processes.
  5. Protect data in transit and at rest — classify data into sensitivity levels and apply mechanisms such as encryption, tokenization, and access control accordingly.
  6. Keep people away from data — reduce or eliminate the need for direct human access or manual processing of data, lowering the risk of mishandling, modification, or human error when handling sensitive data.
  7. Prepare for security events — have an incident management process in place that matches your organization's requirements, running incident response simulations and using tools with automation to increase speed of detection, investigation, and recovery.

These principles are specific to the Security pillar — don't confuse them with the six pillars themselves; a question naming one of these seven by description (e.g., "reduce direct human access to sensitive data") is testing this list, not asking you to name a pillar.

9. Cloud Adoption Framework (AWS CAF) — six perspectives

Used to help organizations plan their journey to the cloud, split into business-oriented and technology-oriented perspectives:

  • Business — Business, People, Governance (ensure business/IT strategy alignment, organizational change readiness).
  • Technical — Platform, Security, Operations (ensure technical readiness across architecture, security posture, and operations).

Four benefits of AWS CAF (exam frames CAF's value around these specifically)

  1. Reduced business risk
  2. Improved ESG (environmental, social, and governance) performance — memorize this specific acronym; it's precise, distractor-bait phrasing the exam likes.
  3. Increased revenue
  4. Increased operational efficiency

Four transformation domains

Separate from the six perspectives above, the AWS CAF also identifies four transformation domains that describe what is being transformed during cloud adoption:

Ordered below as TOPP — a memory hook, not an AWS-defined sequence. The CAF presents these as a set of four, not a ranked or sequential list.

  • T — Technology — migration and modernization of infrastructure, applications, and data platforms to leverage cloud capabilities.
  • O — Organization — evolving organizational structures, staff skills, and culture to operate effectively in the cloud.
  • P — Process — evolving business and IT processes to take advantage of the agility and automation the cloud enables.
  • P — Product — using cloud capabilities to accelerate product development and deliver new value to customers faster.

Exam trap: "which of these is one of the CAF's four transformation domains?" — several plausible-sounding technical terms get offered as distractors here; know why they don't qualify:

  • Networking is a distractor. It's a component within the Platform perspective and the Technology transformation domain, but it is not itself one of the four transformation domains defined by the CAF.
  • Database is a distractor. It's a specific service category within cloud technology, not one of the four transformation domains that the CAF uses to structure cloud adoption activities.
  • Compute is a distractor. It's a specific resource type within cloud infrastructure, not one of the four high-level transformation domains defined by the CAF.

Migration strategies — "the 7 R's" (common exam list, updated from 6)

AWS's original 2016 list had six strategies; AWS later added Relocate as a seventh, distinct from Rehost. Know all seven:

  1. Relocate — move infrastructure to the cloud without purchasing new hardware, rewriting applications, or modifying existing operations — typically a hypervisor-level move (e.g., via VMware Cloud on AWS) at large scale, with zero application changes.
  2. Rehost ("lift and shift") — move as-is onto AWS (e.g., onto EC2), with minimal changes, but not the same specific hypervisor-level bulk move that defines Relocate.
  3. Replatform ("lift, tinker, and shift") — small optimizations without changing core architecture.
  4. Repurchase — move to a different product, often SaaS (e.g., switch a CRM to Salesforce).
  5. Refactor / Re-architect — redesign the application, usually to take advantage of cloud-native features.
  6. Retire — decommission no-longer-needed applications.
  7. Retain — keep as-is on-premises (not yet ready or worth migrating).

10. Pricing, Billing & Support

Pricing fundamentals

  • Pay for what you use — compute, storage, and outbound data transfer are typically billed; inbound data transfer is free in almost all cases.
  • Pay less when you reserve — commitment-based discounts (RIs, Savings Plans).
  • Pay less with volume — the more you use, the lower the per-unit price (economies of scale passed to the customer), e.g., S3's tiered per-GB pricing.
  • Data transfer cost shape (know the general pattern, not exact rates): data transfer IN to AWS is free in virtually all cases; data transfer OUT to the internet is charged (tiered, decreasing per-GB as volume grows); transfer between Regions is charged; transfer within the same Region between AZs typically has a small charge, while transfer within the same AZ can be free.
  • Cost allocation tags — key-value labels (e.g., Project: bfg- platform, Environment: prod) attached to AWS resources, which can then be activated in Billing so cost reports (like the Cost and Usage Report) can be broken down and filtered by tag — the mechanism behind answering "which team/project is spending what." Two types: AWS-generated (e.g., aws:createdBy, automatic) and user-defined (whatever your org decides).

Billing & cost tools

  • AWS Pricing Calculator — estimate costs before deploying.
  • AWS Cost Explorer — visualize and analyze actual historical/ current spend and forecast future spend.
  • AWS Budgets — set thresholds and get alerted when cost/usage exceeds (or is forecast to exceed) them.
  • AWS Cost and Usage Report (CUR) — the most detailed, granular billing data export available.
  • Consolidated Billing (via AWS Organizations) — combine usage across multiple accounts to reach volume pricing tiers faster, with one bill.
  • AWS TCO Calculator — compares the total cost of running on-premises infrastructure vs. AWS.
